# CLAUDE.md

## What this project is

Finds duplicate files anywhere on disk from a start location and organizes them by **source location**, so the user can delete duplicates safely and confidently, individually or in bulk. Example: folder1 and folder2 overlap (fully or partially); the user can choose "delete every file in folder2 that has a confirmed duplicate in folder1".

Four Gradle subprojects (Java 25, Gradle 9.6 wrapper, group `us.pochaev.dfs`):

- `file-scanner`: the core library, hexagonal architecture, a Java module, Spring-free.
- `cli`: Spring Boot CLI. Depends on `file-scanner` via `implementation(project(":file-scanner"))`. It is a primary adapter and the composition root.
- `scanner-spring`: autoconfigure library (package `us.pochaev.dfs.scannerspring`) holding `ScannerAutoConfiguration`, the shared Spring wiring. `cli` and `server` depend on it.
- `server`: Spring Boot web server on localhost (separate from `cli` and `file-scanner`), depends on `file-scanner` and `scanner-spring` (its scan beans and `scanExecutor`, since DFS-040) and has the same ArchUnit guard as `cli`. Planned: an Angular UI in `server/frontend/` for exploring a scan, building a deletion plan and double-checking it, and the folder overlap analysis. So far a skeleton (DFS-035) with its security (DFS-036, U10) and the Angular app (DFS-037): it listens on `127.0.0.1` on a random port, logs `DFS server listening on http://127.0.0.1:<port>/` and `Open http://127.0.0.1:<port>/?token=<token>`, and opens that link in the browser (`dfs.server.open-browser=false` turns that off; tests always do). The token link sets the `DFS_SESSION` cookie (`HttpOnly`, `SameSite=Strict`) by redirect; every `/api/**` request needs it (403 otherwise), the page is public. A filter ahead of Spring Security refuses any `Host` other than `127.0.0.1:<port>`/`localhost:<port>` and any `POST`/`PUT`/`PATCH`/`DELETE` without a matching `Origin`; no CORS. Endpoints: `GET /api/session`, and the scan API in `us.pochaev.dfs.server.scan` (DFS-040): `POST /api/scans` (`{"locations": [absolute paths], "minSize", "defaultExcludes"}`, `201` with `Location`, `400` with `{"code", "message"}`), `GET /api/scans` (this server run's scans, newest first, kept by `ScanRegistry`), `GET /api/scans/{id}`, `POST /api/scans/{id}/cancel`, and `GET /api/scans/{id}/events`, a Server-Sent Events stream of `progress` events (a `ScanProgress` on connect, then at most every 250 ms while it changes, ending with the terminal status); an unknown ID answers `404` `UNKNOWN_SCAN`. The result API in `us.pochaev.dfs.server.result` (DFS-047) serves a COMPLETED scan (`409` `SCAN_NOT_COMPLETED` otherwise): `GET /api/scans/{id}/folders[?parent=]` (the roots, or one folder's subfolders with subtree and direct totals, and `duplicateFiles`/`duplicateBytes`, DFS-059: the subtree's counted files whose content has at least two physical copies, and their bytes) and `GET /api/scans/{id}/sets[?under=&page=&size=]` (duplicate sets, largest reclaimable first, paged, with `totalFiles` and `totalBytes` over every matching set besides `totalItems` and `totalReclaimableBytes`); a `parent` or `under` path must be absolute (`400` `RELATIVE_PATH`) and inside a scan root, else `403` `PATH_OUTSIDE_ROOTS`. The per-scan index is built once and kept by `ScanRegistry.completedState`. The overlaps API, also in `result` (DFS-048), serves a COMPLETED scan's folder overlaps from `us.pochaev.dfs.server.analysis`: `GET /api/scans/{id}/summaries[?under=&page=&size=]` (folder summaries, largest reclaimable first, with `under`'s own summary as `folder`), `GET /api/scans/{id}/pairs[?under=&page=&size=]` (folder pairs, with at least one side under `under`) and `GET /api/scans/{id}/pair?a=&b=` (any two folders; `400` `MISSING_FOLDER` or `NESTED_FOLDERS`, same path rules); the analysis is computed on the first request and kept per scan. The plan API in `us.pochaev.dfs.server.plan` (DFS-054) previews a COMPLETED scan's deletion plan: `POST /api/scans/{id}/plans` (`{"rules": [{keep, quarantineIn}], "exceptions", "picks": [{digest, keep}]}`; every path absolute and inside a scan root, else `400` `RELATIVE_PATH` or `403` `PATH_OUTSIDE_ROOTS` naming the field; the core's `INVALID_RULE`, `UNKNOWN_SET`, `PATH_NOT_IN_SET` and `DUPLICATE_PICK` answer `400`) answers `201` with `Location` and a summary (the core's content-derived `planId`, totals, `leftBehind`, `operationCount`, `conflictCount`); the frozen plan is kept per scan for the server run, `GET /api/scans/{id}/plans/{planId}` reads it back (`404` `UNKNOWN_PLAN`), and `GET .../plans/{planId}/operations` and `GET .../plans/{planId}/conflicts` page its operations and conflicts, largest first (`page`, `size` 1-500, else `400` `INVALID_PAGE`). The registry's listener folds the core's `ScanEvent`s into counts and never blocks the scanning thread. Since DFS-064 a `ScanProgress` also carries `phases` (always present, an empty list before the first phase starts): one `PhaseTotals` per phase that has started, in run order (`WALK` with `directories`, `files`, `bytes` found; `PARTIAL_HASH` and `FULL_HASH` with the `files` and `bytes` of their input, 0 until the first progress; `HARD_LINKS` with `groups`), each with `finished` (true once the next phase has started or the scan is COMPLETED) and kept after the next phase starts, while the flat fields stay; and a `ScanEntry` carries `finishedAt` (required, nullable: null until the scan is COMPLETED, CANCELLED or FAILED, then fixed), stamped from an injectable `Clock` by a 50 ms daemon sweep in `ScanRegistry` (plus a read-time safety net), so it is accurate to about 50 ms; the event stream carries `phases` but not `finishedAt`. The API uses its own records, never core types, so the spec shows only the API. The page is an Angular 22 app with Angular Material in `server/frontend/`, built by the node-gradle plugin with its own Node 24 download under `server/.gradle/` (nothing installed globally; exact versions in `package.json`, installed with `npm ci`): `ng build` output is copied to `server/build/generated/frontend/static/`, a resources directory, so the jar, `bootRun` and the tests serve it, and its Vitest tests (`:server:npmTest`) run in `check`. It shows "Connected" or "Open the link printed in the console" from `/api/session` and, once connected, the scan screen (DFS-041, in `src/app/scans/`): folders as chips, the two settings, Start, and this server run's scans with live progress and Cancel (DFS-057: an unfinished scan shows one line for its current phase, "Finding files" with folders, files and bytes found, "Comparing samples" with files done, left and a percentage, "Hashing files" with files and bytes done, left and a percentage, "Checking hard links" with groups, a bar, a "Found:" line after the walk, and in the hashing phase an ETA from the bytes rate of the last 30 s, "estimating…" at first); the progress stream is read with `EventSource` through `ScanEventsService` (its constructor behind the `EVENT_SOURCE` token, so Vitest supplies a fake), the one call outside the generated client. The page routes with hash URLs (DFS-049; `@angular/router`, `app.routes.ts`): `#/` is the scan screen and `#/scans/<id>` the result screen of a COMPLETED scan (lazy-loaded, in `src/app/results/`), reached from the "Open results" link on a COMPLETED scan row. It is compact and read-only (DFS-060): a header with the scan's folders, its start time, a Compact/Comfortable row-density toggle (Compact by default, kept in local storage behind the `DENSITY_STORAGE` token) and four figures from the unfiltered sets page and the scan entry (Reclaimable, Duplicate sets, Duplicate files, Scanned) over one bar of three segments (reclaimable, last copies kept, unique) with a legend. Left, a lazily loaded folder tree ("All folders" plus the roots; children requested on first expand), each level sorted by duplicate bytes then name, a row showing name, a bar of duplicate over total bytes, size and duplicate size in columns. Right, the Sets tab (selected on open): one grouped table, per set a header row (first file name, "N copies", size each, reclaimable with a bar scaled to the page's largest) then one row per physical copy (short path, modified date, a copy button), hard links as a "N links" badge with the full paths as tooltip, copies under the selected folder badged "in selected", a toggle "All sets" / "Copies under <folder>" and a paginator (25/50/100). ## Commands

Run from the repo root (`./gradlew` works in Git Bash; use `gradlew.bat` in cmd/PowerShell). In shell commands, never start with a bare `cd <dir>`: it moves the session's primary working directory and every later relative command runs from there. Use absolute paths, `git -C <dir>`, or a subshell `(cd <dir> && ...)`.

```
./gradlew build                                   # compile + test everything
./gradlew :file-scanner:test                      # one project's tests
./gradlew :file-scanner:test --tests "*SomeTest"  # one test class
./gradlew -q :cli:run --args="C:/abs/path" > out.jsonl   # scan, write JSONL
./gradlew -q :cli:run --args="C:/a D:/b --format=text"    # scan, print a readable report
./gradlew -q :cli:run --args="C:/a --format=text --output=C:/abs/report.txt"   # write the report to a file instead of stdout
./gradlew -q :cli:run --args="C:/a --progress=log" 2> progress.log   # plain progress lines for a file
./gradlew -q :cli:run --args="C:/a --no-default-excludes"    # also scan .DS_Store, ._* files and the system folders (left out by default)
./gradlew :server:bootRun                         # start the local server; open the URL it logs
./gradlew :server:bootJar                         # server/build/libs/dfs-server.jar
./gradlew :server:installBootDist                 # server/build/install/dfs-server-boot/bin/dfs-server(.bat)
./gradlew :cli:installBootDist                    # cli/build/install/dfs-boot/bin/dfs(.bat); README: installing outside the repo
./gradlew :server:npmTest                         # the Angular unit tests (Vitest) alone
./gradlew :server:updateOpenApi                   # rewrite server/frontend/openapi.json after changing a controller
./gradlew :server:e2eTest                          # the browser flows (Playwright, real Chromium); first run downloads the browser
./gradlew :server:bootRun --args=--server.port=8080   # frontend development: the server on a fixed port, then
./gradlew :server:npm_run_start                   # ng serve on http://127.0.0.1:4200, proxying /api to port 8080
```

For frontend development, open the server's `Open ...?token=` link once, then `http://127.0.0.1:4200`: the session cookie is not tied to a port, and the dev server reloads on every save (DFS-037 decision 4). The proxy rewrites `Origin` to `http://127.0.0.1:8080`, so `POST`s pass the server's check; the `SameSite=Strict` cookie still keeps other sites out (DFS-040 decision 5). Use `127.0.0.1`, not `localhost`, for both.

`:cli:run` starts in `cli/`, so pass **absolute** paths. `-q` keeps Gradle's own lines out of stdout, which must carry only the output. Stdout is always UTF-8; to see non-ASCII paths correctly on a Windows console, switch it to UTF-8 first (`chcp 65001` in cmd, `[Console]::OutputEncoding = [Text.Encoding]::UTF8` in PowerShell). In Windows PowerShell 5.1, `>` re-encodes a program's output as UTF-16 and mangles non-ASCII paths, so use `--output=<file>` (an absolute path) there instead of `>`: the report is written as UTF-8, an existing file is replaced only by a complete report, and stderr ends with `Report written to <path>`. Progress goes to stderr, by default as one line per phase redrawn in place (`--progress=live`); use `--progress=log` when stderr goes to a file and `--progress=off` for none. Gradle 9.6 on JDK 25 prints a harmless "restricted method in java.lang.System" warning at startup. The scanner calls native code on Windows; every launcher passes `--enable-native-access=ALL-UNNAMED` (or the `Enable-Native-Access` manifest attribute), and an embedding app must do the same.

Shared config (Java 25 toolchain, `--release 25`, JUnit 6 BOM, `useJUnitPlatform`) lives in the root `build.gradle.kts` `subprojects {}` block; do not repeat it in subprojects.

## `file-scanner` architecture

Base package `us.pochaev.dfs.scanner`, module name the same.

```
domain.model              data structures (records, sealed interfaces); depends on nothing
domain.usecases.query     primary query ports (CQS)
domain.usecases.command   primary command ports (CQS)
domain.factory            static factories; the ONLY domain package allowed to touch application/infra
application               business logic + domain services; implements the use cases
infra.port                secondary ports
infra.adapter             secondary adapters (NIO filesystem, hasher, quarantine deleter, ...)
```

Any layer, and the top level, may have a `util` package for shared helpers. A `util` package may only depend downward or on the JDK, never on the layer above it.

**Dependency rules** (enforce with ArchUnit tests; `module-info` cannot express these):

- `domain.model`: no dependencies.
- `domain.usecases.*`: `domain.model` only.
- `application`: `domain.model`, `domain.usecases`, `infra.port`.
- `infra.adapter`: `infra.port`, `domain.model`.
- `domain.factory`: may also depend on `application` and `infra.adapter`. This is the one deliberate exception; nothing else in `domain` may.

**Module exports.** `module-info.java` exports each `domain.*` package individually (JPMS has no recursive export). `application` and `infra.*` are never exported.

**Important caveat.** JPMS encapsulation is not enforced when the consumer runs on the classpath, and Spring Boot (fat jar, `bootRun`, tests) always does. `cli` and any future server could compile against `application`/`infra` classes and nothing in the toolchain would stop it. So:

- Add an ArchUnit rule in every consuming app forbidding dependencies on `..scanner.application..` and `..scanner.infra..`.
- Keep `module-info` anyway: it documents intent and supports modular consumers/jlink.

## Design decisions (settled)

1. **Location model.** Overlaps are computed per immediate-directory pair and rolled up, so the user can also pick any ancestor folder (recursive) as keep or delete source. Two views of one result: `DuplicateSet` (identical content, N paths) and `LocationOverlap(A, B)` (which files in B have a copy in A; all vs partial). The scanner does not compute `LocationOverlap`: an analysis tool does, from the JSONL export (DFS-030; `tools/analysis/overlaps.sql`, design in `docs/design/folder-overlap-analysis.md`). The scan records what that needs: the scanned roots and each folder's direct file count (`ScanResult.roots`, `ScanResult.folders`).
2. **Deletion.** Files are moved to an app-managed **quarantine folder** with a manifest (original path, keeper it was verified against) that doubles as the audit log; a whole run can be undone, and a purge command frees space. A permanent-delete adapter exists behind the same `FileDeleter` port, selected by an explicit flag. Do not use `java.awt.Desktop.moveToTrash`.
3. **Detection pipeline.** Group by size, then a partial hash (head and tail, about 64 KB each), then full SHA-256 for files still matching. Drop groups of one after each stage. Skip the partial stage for small files (under about 128 KB), and hash in path order within a group (spinning-disk locality). A persistent hash cache (path + size + mtime) is deferred; it would sit behind a port.
4. **Delete-time proof.** Immediately before quarantining a file, re-verify with a **byte-for-byte compare against the keeper** (`ContentComparator` port). No skip flag for now. This also catches files that changed after the scan.
5. **Factories.** Plain static factories in `domain.factory` that instantiate application/adapter classes directly (compile-time checked, works on classpath and module path). No `ServiceLoader`. Callers depend only on the factories' static API, so the internals could later move to ServiceLoader unnoticed.
6. **Spring wiring.** The scanner has no Spring dependency. Done in DFS-031: `scanner-spring` holds `ScannerAutoConfiguration`, whose `@Bean` methods call the factories, with `@ConditionalOnMissingBean` so an app can override the executor (by name `scanExecutor`), `ScanUseCases` and each port. `@ConfigurationProperties` arrives with the first app-wide setting.

## Safety invariants (must hold, and be tested)

- **Never delete the last copy.** Every `DeletionPlan` must leave at least one verified surviving copy per `DuplicateSet`. Rules can conflict (folder1's copy may itself be marked for deletion by another rule), so validate the plan as a whole, not rule by rule.
- **One plan execution runs at a time**, per process (a second start is refused with `EXECUTION_ALREADY_RUNNING`) and per manifest folder across processes (an OS lock on `<manifest folder>/execution.lock`, DFS-055); processes with different manifest folders are not coordinated.
- **Re-verify at execution time:** the keeper and the candidate still exist and are unchanged, and content is byte-identical (decision 4).
- **Preview is a pure query; execution is a separate command.** `PreviewDeletionPlan` never touches disk state.
- **Hard links are not duplicates.** Paths that are the same physical file must not count as copies of each other. Identify them by a key per file (`FileIdentity.key`), grouped within a candidate set: `fileKey()` (device and inode) on Linux and macOS; on Windows, where `fileKey()` is null (verified), the volume serial number and 128-bit file ID from `GetFileInformationByHandleEx(FileIdInfo)` through the FFM API. Never compare pairwise: a set of n plain copies would cost n²/2 checks (DFS-026).
- **Do not follow symlinks or junctions by default** (avoids cycles), and skip cloud placeholders (e.g. OneDrive) by default, since reading them triggers a download. On Windows a junction reports `isDirectory=true, isSymbolicLink=false, isOther=true`, and `Files.walk`/`walkFileTree` descend into it anyway (verified: files appear twice). The walker adapter must detect reparse points itself (`isOther()` directories and symlinks) and skip the subtree.
- **Scans leave quarantine folders out** (DFS-052): the walker never enters a plain directory named exactly `.dfs-quarantine` (case-sensitive, any depth) and reports it as skipped with `QUARANTINE`, always, also with `--no-default-excludes`; `StartScan` refuses a location with that name among its path's elements (`LOCATION_IN_QUARANTINE`, by name, before any disk lookup). So quarantined files are never reported as duplicates and a plan cannot target them.
- **Scans leave operating-system folders out** (DFS-061): the walker never enters a plain directory below a scan root named `$RECYCLE.BIN`, `System Volume Information`, `Recycled`, `RECYCLER` (Windows, any letter case), `.Trashes`, `.Spotlight-V100`, `.fseventsd`, `.TemporaryItems`, `.DocumentRevisions-V100` (macOS), `.Trash`, `lost+found` or `.Trash-<digits>` (Linux, exact), at any depth, and reports it once as skipped with `SYSTEM_FOLDER`. Unlike `QUARANTINE`, `--no-default-excludes` (`ScanConfig.defaultExcludes` false) switches it off; a scan root itself, or inside such a folder, is always walked. `Thumbs.db` and `desktop.ini` are still not skipped.
- Exclude empty (0-byte) files by default; a minimum-size setting generalizes this.

## Provisional port sketch (revise as it is built)

- Commands: `StartScan` (returns a scan ID immediately), `CancelScan`, `ExecuteDeletionPlan`, plus undo/purge of a quarantine run.
- Queries: `GetScanStatus`, `ListDuplicateSets`, `ListLocationOverlaps`, `PreviewDeletionPlan`.
- Secondary ports: `FileTreeWalker`, `ContentHasher` (sample and full), `ContentComparator`, `FileDeleter`, `ScanRepository`.

`FileTreeWalker` is built (`walk(Path root, WalkListener)`, implemented by `NioFileTreeWalker` on `Files.walkFileTree`). It is callback-based rather than returning a `Stream` so it reuses the JDK's cached directory-listing attributes and reports errors through hooks; the listener returns `false` to stop (this is how cancellation reaches it). It emits `WalkEvent.FileFound(FileEntry)` for each regular file and `WalkEvent.Skipped(path, SkipReason, detail)` for everything left out (`SYMLINK`, `SPECIAL_FILE`, `UNREADABLE`, `QUARANTINE`). One rule on every platform: yield only regular files, descend only into plain directories, never follow links. A link given as the root itself is resolved and its target walked. Empty files are yielded; filtering by size belongs in `application`.

## Spring-friendliness rules for the scanner

- No Spring types or annotations in `file-scanner` (no `@Component`, no `@Async`).
- A config record in `domain.model` (minimum size, symlink policy, quarantine folder, parallelism) that `@ConfigurationProperties` can map onto.
- Factories return port interfaces and accept optional overrides for secondary ports (tests, the server).
- The executor is supplied by the caller (virtual threads for the CLI, Spring's `TaskExecutor` for a server).
- Scan state lives behind `ScanRepository` (in-memory adapter first) so several concurrent scans work; no state in singleton fields.
- Progress is reported through a listener, never printed by the core.

## Code and test conventions

- Java 25: records for data, sealed interfaces for results and variants. Do not enable preview features (`StructuredTaskScope` is still preview).
- Test `application` against fake or in-memory adapters (JimFS or hand-written fakes) rather than the real disk.
- Keep the ArchUnit layering tests green; they are the real enforcement of the rules above.
- Test fixtures: `file-scanner/src/test/resources/fixtures/` holds only what git stores portably (regular files and directories: empty files, Unicode and odd names, deep nesting, same-size-different-content, duplicates across folders). Tests copy it into a `@TempDir` (`Fixtures.copyInto`). Never commit anything platform-specific there: symlinks, hard links and junctions do not survive git or a Windows checkout, empty directories are not tracked, and Windows forbids case-only variants and some names. Create those at test time, and skip the test (`Assumptions`) when the platform or privileges do not allow it. `.gitattributes` marks fixtures `-text` so bytes are identical everywhere; keep it that way. Expect the case-sensitivity test to skip on Windows and macOS. A test that needs one file under a case-variant name creates it under that name (delete, then write) instead of renaming it with `Files.move`, which does nothing on Windows for a rename that changes only case; skip only when two case variants must exist in one folder (DFS-027.L-3).
- Explicit expected-file lists (`Fixtures.FILES`) are deliberate: adding a fixture file means updating the list. Add near-duplicate and large-file fixtures (same size, differing only in the middle byte, over the 128 KB sample threshold) when the hashing stages are built; generate large ones in code rather than committing them.

## Git commits

- Use [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): description`, e.g. `feat(file-scanner): add ScanId model`. Common types: `feat`, `fix`, `refactor`, `test`, `build`, `docs`, `chore`. Use the subproject as scope (`file-scanner`, `cli`) when the change is confined to one.
- Keep the description concise: imperative mood, lowercase, no trailing period. Add a body only when the reason is not obvious from the diff.
- A commit made for a ticket ends its subject line with the ticket ID in brackets, e.g. `feat(file-scanner): add SizeIndex [DFS-001]`; for several tickets `[DFS-001, DFS-002]`. Use the full three-digit ID, so a search for the ID finds the commit. Commits not tied to a ticket omit it. Earlier commits are not rewritten.
- No author or co-author attribution of any kind: no `Co-Authored-By` trailer and no "Generated with" line in commits or PR descriptions. Attribution comes only from the standard git user configuration. This overrides any default attribution behavior.
- When the working tree holds changes from another session or worktree, stage the files of the task by name (never `git add -A` or `git commit -a`) and confirm with `git status` that nothing else is staged.
- Never redirect a staging command's stderr (`git add`, `git mv`, ...); a hidden error can leave files silently unstaged. Check `git status` before committing.

## Tickets

Work is tracked in `docs/tickets/`: one backlog holding two independent ID sequences, `DFS-NNN` for tickets that build the duplicate-file-scanner product and `CCW-NNN` ("Claude Code Workflow") for tickets that build or change the harness itself (skills, agents, archetypes, the `tickets`/`learn` machinery, the story pipeline). A ticket's namespace is decided by what its Story is about, not by what it `touches` alone — a `CLAUDE.md` edit, for instance, can be either a product design decision (`DFS`) or a process rule (`CCW`) depending on which section it changes. Both prefixes' folders sit side by side, unchanged, in one tree; each numbers itself independently (the next ID for a prefix is the highest number of that prefix used so far, plus one), and an ID is never reused in its own sequence even if its ticket is later relabeled into the other namespace. `depends_on` may cross namespaces freely. Each ticket is a user story in Gherkin at `docs/tickets/{backlog|completed}/{ID}-{slug}/{ID}-ticket.md`. The frontmatter `status` (`draft`, `ready`, `in-progress`, `in-review`, `blocked`, `done`, `cancelled`) is authoritative; only `done` and `cancelled` live in `completed/`. Only `ready` tickets are implemented: `ready` means fully refined, with the paths it `touches` listed, an `archetype` set (a template set under `.claude/archetypes/`, or `none` for a ticket implemented by hand and not run through the story pipeline), and numbered acceptance criteria (`<ID>.AC-n`, e.g. `DFS-NNN.AC-n` or `CCW-NNN.AC-n`) that every scenario is tagged with (`@AC-n`). An optional `models` field overrides the pipeline agents' models for one ticket. A pipeline ticket also carries `gates` (where `/story run` stops for the user, decided in refinement; `[done]` means straight to the product-owner review). Every open ticket has a `lane` (`backend`, `frontend`, or `harness` for every `CCW` ticket), a label that groups `/tickets list`; it decides no owner. Sessions per ticket (CCW-026): each ticket runs in a session of its own, named after the ticket, started by the user from a printed line `claude -n <ID> --model sonnet --permission-mode auto "<command>"` (`--model sonnet` only for a ticket whose archetype is not `none`; CCW-033) (printed by `refine`'s ready commit, every story stop, `done` for the tickets its close unblocked, and `list`); that session runs the whole ticket, `done` included, and no session starts another or messages another. `docs/tickets/lanes.md` holds only the role `coordinator` (CCW-021): that session writes and refines tickets in every lane but never starts, launches or closes one, and no session reports to it; it catches up from git and the working trees through `tools/story-gate/story-gate catch-up`, run by a SessionStart hook in `.claude/settings.json` (printing only in the session whose name, the hook input's `session_title` or else `DFS_SESSION`, maps to `coordinator`) and by its `/tickets list`. Context hygiene (CCW-022): a session ends each ticket boundary (`done`, `refine`'s ready commit, a story stop) with the launch line for the next command after writing anything only the chat holds to disk, the `story` skill commits `plan.json` before every stop, `/compact` is for the middle of a ticket (template in the `tickets` skill), and any non-coordinator session's `/tickets list` runs `story-gate catch-up --session <name> --lanes`, listing every started ticket of every lane. Use the `tickets` skill (`/tickets new|refine|list|start|review|done|...`, in `.claude/skills/tickets/`) instead of editing by hand. An agent implementing a ticket reads only that ticket and this file, stays within `touches`, and reports instead of editing outside it.

A ticket worked off `main` uses branch `tickets/<ID>-<slug>`, and if it has a worktree, `../<repo-dir>-<ID>-<slug>` beside the checkout (`/tickets start <ID> --worktree` creates or enters it and makes the status edit there). `/tickets done` closes on `main`: it merges the branch unless it has already landed, then commits the close itself as `docs: close <ID> [<ID>]`. That commit needs no separate confirmation, because running `/tickets done` is itself the request. Removing the worktree and branch comes after one confirmation, never forced. For parallel work, keep the repo checkout on `main` and run every ticket in its own worktree. If nothing has `main` checked out, `done` opens a temporary close tree for it, so no session has to switch branches.

## Current state and open items

- The package layout, `module-info.java` and ArchUnit tests are scaffolded (ArchUnit 1.5.0, core artifact with plain JUnit tests; not `archunit-junit5`, to avoid engine compatibility risk with JUnit 6). `cli` is a Spring Boot app (an `ApplicationRunner`, arguments parsed by hand) that scans the folders given and writes JSON Lines to stdout in the order `scan` (header: `schemaVersion`, roots, settings, start and finish times), `folder` (one per folder with its direct counted-file count and bytes), `set` (each copy path an object with `path` and `modified`), `skipped`, then one `summary` line; progress and errors go to stderr; exit codes 0, 1 and 2. The schema and rules are in DFS-030 (earlier: DFS-020). `schemaVersion` is an integer, currently 2 (a file with no `scan` line is version 1); it is bumped only when something existing changes meaning or shape, never for new fields or line types, and readers ignore fields and line types they do not know. `--format=text` prints a readable report instead (largest reclaimable space first; DFS-023). Stdout is UTF-8 in both formats; `--output=<file>` writes the report to a file instead (DFS-029). The `summary` line (and the text report's last line) ends with an `excluded` count: files left out by name by default (`.DS_Store` and `._*`, case-sensitive; DFS-027), 0 with `--no-default-excludes`. `--no-default-excludes` also scans the operating-system folders (DFS-061, invariants above). Progress (DFS-024) shows folders, files and bytes found, then files and bytes hashed with a percentage and ETA, from the scanner's `ScanEvent`s (`DirectoryWalked`, `FileWalked` with bytes, `HashProgress`, `GroupDone`); `--progress=live|log|off`.
- `scanner-spring` (DFS-031) has its own `ArchitectureTest`: it may not depend on `..scanner.application..` or `..scanner.infra..`. `cli` has no scanner beans of its own.
- Guards: `file-scanner` has `ArchitectureTest` (layers, top-level `util`, no Spring) and `ModuleExportsTest` (reads the compiled `module-info.class`: only unqualified `domain.*` exports, every non-`util` domain package exported, nothing opened). `cli` has an `ArchitectureTest` that forbids depending on anything under `us.pochaev.dfs.scanner` outside `domain`.
