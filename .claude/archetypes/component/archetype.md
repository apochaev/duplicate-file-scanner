# component

Applies to a ticket that adds or changes an Angular screen or component in `server/frontend`: standalone components with their templates and styles, the services and small wrappers they need, client-side formatting and validation, and their Vitest tests. Example: DFS-041, the scan screen (a form with folder chips and settings, a live list of scans, a stream wrapper).

It does not apply to:
- an HTTP endpoint or a change to the API's records (`endpoint`); a screen that needs a new or changed endpoint is two tickets, the endpoint first, or a request to the lane that owns it. Regenerating the client for an endpoint that already exists is part of the screen's ticket;
- a core use case (`use-case`) or Spring wiring (`wiring`);
- the security rules (DFS-036: `SecurityConfiguration`, `HostOriginFilter`, the token exchange) or how the server serves the page (the `ng build` output as static resources, DFS-037);
- the frontend build itself (`angular.json`, the Gradle tasks): a build ticket built by hand, like DFS-044. A runtime package of the same Angular release that a screen needs (for example `@angular/router`, DFS-049 decision 7) may be added to `package.json` and `package-lock.json` in a component ticket that lists them in `touches`; any other dependency or build change is a build ticket.

Written from DFS-037 (the Angular app), DFS-038 (the generated client), DFS-041 (the scan screen) and DFS-044 (the budget and font), all built by hand because no archetype fit; proven by a dry run against DFS-041 and a real gate run on a throwaway ticket (CCW-020 `dry-run.md` and `verification.md`). Its first live use is the next frontend screen ticket.

## Where files go

- **One folder per feature** under `server/frontend/src/app/`, for example `src/app/scans/` (DFS-041): the components (`scan-screen.ts`, `.html`, `.css`), their small services (`scan-events.service.ts`), pure helpers (`scan-format.ts`) and the feature's specs (`scan-screen.spec.ts`). File names are kebab-case; class names have no `Component` suffix (`ScanScreen`, selector `app-scan-screen`), as Angular 22's CLI writes them.
- **Standalone components with signals.** `signal`, `computed`, `linkedSignal`, `input()`, `output()`, `inject()`; the template's `@if`, `@for` (with `track`) and `@empty`; no `NgModule`, no zone (the app is zoneless). Templates and styles in their own files (`templateUrl`, `styleUrl`). A component's style stays under the `anyComponentStyle` budget (4 kB warning).
- **The API only through the generated client** (DFS-038). Inject the services under `src/app/api/services` (`ScansService`, `SessionService`) and use the models under `src/app/api/models`; their methods return Promises. `src/app/api/` is generated by `ng-openapi-gen` before every build, test and serve, git-ignored, and never edited by hand. A screen needing an endpoint that does not exist yet is blocked on an `endpoint` ticket.
- **Anything the browser has and jsdom lacks goes behind an injectable wrapper with an `InjectionToken`** (DFS-041 decision 5): `EventSource` today (`EVENT_SOURCE` in `scan-events.service.ts`, opened by `ScanEventsService`). The token's default factory uses the browser's API; a spec provides a fake through the token. This is the only way around the generated client, and only for what it cannot do (a Server-Sent Events stream).
- **Stubs**, owned by the architect: each component method, service method or helper function a criterion's behavior goes through throws `new Error('not implemented: <TICKET-ID>')`. Signatures, `input()`/`output()` declarations, injected dependencies, the template's structure and its CSS classes are final: the test-author writes tests against them. Copy `skeletons/feature.ts.tmpl` and `skeletons/feature.html.tmpl`, replacing every `<...>`; `skeletons/feature.spec.ts.tmpl` is the test-author's (`test-guide.md`), and the architect writes no spec (DFS-050.L-1). The architect confirms the stubs compile with `./gradlew :server:ngBuild`.
- **Tests** sit beside the code as `*.spec.ts` (see `test-guide.md`). Every story spec uses the shared helper `src/testing/stub-surfacing.ts` (`provideStubSurfacing()`, `settle(fixture)`); the gate counts `src/testing/` as test code, so it is frozen after the test phase like the specs.
- **The page shell** is `src/app/app.ts`/`.html`: it shows a screen once `/api/session` says connected (DFS-041 decision 6). A new screen is placed inside the shell or an existing screen, or gets a route: the page routes with hash URLs (DFS-049 decision 1; `provideRouter(routes, withHashLocation())`, routes in `src/app/app.routes.ts`, `#/` is the scan screen), so the server needs no fallback for them. A heavy screen (tree, tabs, paginator) is loaded lazily with `loadComponent`.

## Edge-case checklist

Work through every item; mark one that does not apply with a one-line reason in `design.md`'s "Checklist disposition".

1. **The generated client** (DFS-038, DFS-041 decision 5). Which service methods does the screen call, with which request bodies and which models back? Does the screen need anything the API does not offer yet (then it is blocked on an endpoint ticket, not built around)? Is `src/app/api/` untouched? An optional setting the user left alone is left out of the request, so the server's default applies (DFS-041 decision 3).
2. **Promise timing in tests** (DFS-038). The generated client returns Promises; a test that reads the page before they settle sees the old state. Every test lets them settle with `settle(fixture)` from `src/testing/stub-surfacing.ts` after each step, never a bare `fixture.detectChanges()`.
3. **Stubs reachable and surfaced** (CCW-020 decision 7, DFS-027.L-2). Through which stub does each criterion's behavior go? A test that never reaches a stub passes or fails on an assertion, and the red gate rejects both. A stub's error reached from a template, an event handler or a Promise callback is swallowed by Angular's `ErrorHandler` or an unhandled rejection unless the spec uses `provideStubSurfacing()` and `settle(fixture)`. A new directive or injected service in an existing component (a `routerLink` needs the router's providers) makes every existing spec that renders it without those providers fail with another error: run `:server:npmTest` once after the stubs compile and list each such spec under `design.md`'s Expected breakage (DFS-049). Do not reach a stub from an RxJS subscriber callback (`subscribe`'s `next`): RxJS rethrows its error from a timer, outside Angular's `ErrorHandler`, so `provideStubSurfacing()` does not see it. Feed the stub from an `effect`, whose errors reach the `ErrorHandler`. In an existing spec without `provideStubSurfacing()`, Vitest also prints an "Unhandled Errors" block (shown as "Uncaught Exception" entries) for that stub; the red gate does not count it as a separate regression (DFS-057.L-2).
4. **Browser APIs jsdom lacks** (DFS-041 decision 5). Does the screen use `EventSource`, `ResizeObserver`, `IntersectionObserver`, the clipboard, `matchMedia` or anything else jsdom does not implement? Each goes behind a wrapper with an `InjectionToken` and a fake in the spec that the test drives step by step.
5. **Where the screen sits and when it shows** (DFS-041 decisions 2 and 6). Which component hosts it (the shell, or an existing screen)? Does it show only when connected? Does it need a route (a hash route in `app.routes.ts`, eager or lazy with `loadComponent`, DFS-049), and which links lead to it (`routerLink`)?
6. **Input and validation** (DFS-041 decisions 1 and 3). How each value is entered (a chip per absolute path, a number with a unit), what the form refuses itself and with which message, what it sends for an untouched field, and where a server code (`RELATIVE_LOCATION`, `INVALID_MIN_SIZE`) is shown (next to its field).
7. **Loading, empty and error states** (DFS-041 AC-4, AC-9, AC-10). What the screen shows while loading, with nothing to show ("No scans in this server run yet"), when a load fails, for a `400` with the server's `{code, message}`, for a `503` (`EXECUTOR_REJECTED`: "The server is busy, try again"), and without a session (`403`). Errors use `role="alert"`; regions and lists have labels a test and a screen reader can find.
8. **Live updates** (DFS-041 decision 5, DFS-040 decision 3). For a stream: when it opens (only for a resource still changing), what each event updates, when it closes (terminal status, unsubscribe, component destroyed), what a reconnect does (the server sends the current state on connect) and what the screen shows when the browser gives up ("Live progress lost; reload the page").
9. **Material components and their harnesses** (DFS-041). Which Angular Material components (chips, expansion panel, button toggle, checkbox, progress bar, button), imported per component. Tests drive them through their harnesses (`@angular/material/<x>/testing`, `TestbedHarnessEnvironment`), not through Material's internal DOM. A tab whose content loads data: content placed directly in a `mat-tab` is created once and only detached; `<ng-template matTabContent>` creates it when shown and destroys it when left (DFS-050.L-4).
10. **The bundle budget and the system font** (DFS-041, DFS-044). Does a new Material module or dependency push the production build's initial bundle toward the 1 MB warning (DFS-044 decision 1)? The build output is checked for a budget line. Measure the initial total again after the stubs compile, since they already import every module; a screen that pushes it toward the warning is loaded lazily (DFS-049: eager 896 kB, lazy 697 kB). Text uses the theme's typography tokens, which `styles.css` sets to `system-ui, sans-serif` (DFS-044 decision 2); no web font is loaded (the page loads nothing from the internet).
11. **The live check reads the DOM** (DFS-041). The screen is checked once by hand on the built jar (`java -jar server/build/libs/dfs-server.jar --dfs.server.open-browser=false`, the logged `?token=` link). What it shows is read from the page's DOM (computed text and styles through the browser's JavaScript), never from a screenshot alone: screenshots of a background window can lag behind the DOM. Tabs opened for it are closed afterwards, and the server is stopped by its PID. For a progress or ETA screen, the live check needs a scan that reaches the slow phase quickly: name a folder of a few large duplicate files in the ticket's done-item, not a large tree of small files (a 100 000-file tree spent minutes in the sample phase from a cold cache, DFS-057). A browser driver is Playwright for Java run from the Gradle cache (`playwright`, `driver`, `driver-bundle` and `gson` jars) with `setChannel("msedge")`, so no Chromium download; under Git Bash the `-cp` paths must be `C:/...`, not `/c/...` (DFS-057.L-3).
12. **The dev server and its proxy** (DFS-037 decision 4, DFS-040 decision 5). For iterating on styles: `./gradlew :server:bootRun --args=--server.port=8080`, then `./gradlew :server:npm_run_start` on `http://127.0.0.1:4200` (use `127.0.0.1`, not `localhost`). The proxy rewrites `Origin`, so `POST`s pass the server's check. `ng serve` outlives its Gradle task; stop it by the PID listening on port 4200.
13. **Docs** (DFS-041). The `CLAUDE.md` `server` entry says what the page shows; `docs/design/ui.md` describes the screen under its U-section and marks its item done.

## Extra done-items

Beyond the standard checks (every scenario automated and passing, `./gradlew build` green including ArchUnit and module-export tests, no files changed outside `touches`):

- Every checklist item is addressed in `design.md` or marked not applicable with a one-line reason.
- The production build prints no budget warning (checklist item 10).
- Every story spec uses `provideStubSurfacing()` and `settle(fixture)` (checklist item 3).
- Checked by hand once on the built jar, the screen's text and states read from the DOM (checklist item 11), and the result recorded in `verification.md`.
