# DFS-060 learnings

- **design / architect**: a stub reached from a routed component's constructor (here `readDensity` in a field initializer of `ResultScreen`) does not fail `app.routes.spec.ts` with the stub's error. The router swallows the error during navigation, and the test times out or leaves a request open. The archetype's checklist item 3 covers specs that render the component directly. It could add that a lazily routed component's constructor stubs show up in the routes spec as a timeout, so that spec goes under Expected breakage, or the stub moves to a template-evaluated method.
- **design / architect**: the ticket's Context named only DFS-053's AC-3 and AC-5 browser flows as affected. Decision 5 (the copy button copies the full path) also changes DFS-053.AC-7, the flow at line 209 (Overlaps selected), the `.selected-label` count and the folder helper's `name + " ·"` filter. Refinement could grep `BrowserFlowTest` for every selector and text the decisions replace, as the architect does for the Vitest specs (DFS-057.L-1).
- **test / test-author**: the ticket's AC-7 scenarios assume a 36-character budget, but the screen has one fixed `PATH_BUDGET = 62`, so the budget-36 examples can only be tested on `displayPath` itself; screen-level specs need longer paths. Refinement could say which level a scenario's budget belongs to.
- **test / test-author**: `app.routes.spec.ts` (two DFS-049.AC-1 tests) fails against the stubs with a timeout and a TestBed error, not the stub's message, as design.md predicted; the red gate must accept it as expected breakage because it is not a DFS-060 test.
- **test / test-author**: `expect(() => stub()).not.toThrow()` turns the stub's `not implemented` error into an AssertionError and fails the red gate. A "never throws" scenario has to call the function bare and assert on an observable afterwards. The component archetype's `test-guide.md` could say so.
- **test / test-author**: AC-9's "open again" cannot be a second navigation to the same URL in `RouterTestingHarness` (a same-URL navigation is ignored); it is tested as a pre-filled fake storage instead.
- **implement / implementer**: `.folder-pin` was `position: absolute` over the row, so even at opacity 0 (and fully visible on hover) it sat on top of `.folder-select` and Playwright's click on a folder was intercepted (DFS-053.AC-4 timed out). Moved it into the row's flow (flex item, smaller text) in `folder-tree.css`; costs about 110 px of the row.
- **implement / implementer**: `BrowserFlowTest` DFS-053.AC-6 (`pinCompareAndUnpin`) asserts `.pinned-folder` right after pinning, but with Sets selected on open the `Pinned:` label lives in the Overlaps tab (matTabContent), so it is not in the DOM. The test needs `tab("Overlaps").click()` after pinning (frozen test, reported as a defect; the design's Expected breakage list missed it).
- **verify / verifier**: Vitest and Playwright assert that `.folder-name` and `.short-path` text is in the DOM, not that it is visible, so two layout defects passed every gate: the folder tree's name column is squeezed to 0 px (the always-in-flow, invisible "Pin for comparison" button takes about 110 px, and the grid's three fixed columns take the rest of the ~270 px tree), and the 62-character `PATH_BUDGET` does not fit the ~300 px path column inside the app shell's ~960 px content width, so CSS clips the end of the path and hides the file name the path rule exists to keep. The archetype's checklist item 11 caught them only in a screenshot. A design could size the budget from the column it renders into (or the column from the budget), and a Playwright flow could assert `isVisible()`/bounding-box width on `.folder-name` and on `.path-name`.
- **verify / verifier**: `POST /api/scans` from Git Bash curl: a JSON body with backslash paths was mangled to an invalid escape twice; forward slashes (`C:/...`) work and the server reports links with backslashes anyway. Headless `chrome --dump-dom --virtual-time-budget=8000` on the `?token=...#/scans/<id>` link renders the result screen without Playwright (the fragment survives the token redirect), which is enough for a DOM read and `--screenshot`.
- **verify / verifier (re-check after the layout fix)**: the fix commit moved the pin out of the row's flow, but the folder name stayed invisible. The cause was never only the pin: the tree column is about 256 px, and the row grid's fixed columns (3.5rem + 4.5rem + 4.5rem plus gaps, about 224 px) plus the 32 px toggle leave nothing for `minmax(0, 1fr)`. The path fix (`.sets-tab { display: inline-block; min-width: 62ch; overflow-x: auto }`) un-clipped the file names but made the table wider than its tab, adding a horizontal scrollbar. That pushes the Reclaimable bytes out of view and wraps the Modified dates. A fix that reports "build green, e2e 8/8" is not evidence for a visual defect: the implementer should take a screenshot of the built jar too, or the e2e flows should assert a non-zero bounding box for `.folder-name`, `.path-name` and `.set-reclaimable-bytes` within the viewport.
- **implement / implementer (second reopen)**: departures from design.md: `PATH_BUDGET` is 56, not 62. The sets-tab spec allows 55-63, and 56 characters at 0.75rem monospace fill the ~430 px File column. The tree rows are two lines, because the ~256 px column cannot hold a name plus three fixed columns on one line. The template got a `.copy-path-line` wrapper (no tested class changed) and an indent of 12 instead of 16. For the live check, headless Chrome with `--remote-debugging-port` driven by a short Node script over CDP (the project's own `server/.gradle/nodejs` node, which has a global `WebSocket`) can expand the tree, hover, read `getBoundingClientRect`/`scrollWidth` and take screenshots. `--dump-dom` cannot click.
- **verify / verifier (final re-check)**: `document.elementFromPoint` at the centre of each `button.folder-select` catches what a by-eye check cannot see. At 800 px (the one-column layout below 960 px), every row centre hits the invisible `folder-pin` button through Material's `.mat-mdc-button-touch-target`, which reaches far beyond the pin's 110 x 16 px box, so a click in the middle of a folder pins it. `opacity: 0` does not take an element out of hit-testing. The e2e flows run only at desktop width, so they cannot see it. A live check for a component with hidden-until-hover controls should hit-test at one narrow and one wide viewport, and a Playwright flow could repeat one row click at a narrow viewport. Earlier lesson confirmed: keep the measuring script in its own scratch folder and give each headless Chrome its own `--remote-debugging-port`, because reusing a port right after killing Chrome got `ECONNRESET`.
