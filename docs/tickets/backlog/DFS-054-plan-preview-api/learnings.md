# DFS-054 learnings

- **architect, read scope vs a mapping endpoint** (design phase): `architect.md` limits reading to `touches` and the archetype's "where files go", but an endpoint over an existing core use case maps the core's `domain.model` types into its own records, and DFS-054's conflict join (decision 4: which rule keeps or would quarantine each copy) has to mirror the core's rule exactly. So I read `PreviewDeletionPlan`, `DeletionPlan`, `Operation`, `Conflict`, `Source`, `PlanRequest`, `KeepAndQuarantine`, `KeepCopy`, `LeftBehind` and `PreviewDeletionPlanService` (read-only, outside `touches`). Suggest the endpoint archetype's "where files go" (or `architect.md`) allow reading the `domain.model` types and the use-case port an endpoint maps from, and the service only when the ticket asks the server to re-derive core semantics.
- **ticket wording left a semantic open** (design phase): AC-4's "the rules that would quarantine it or keep it" reads either as "the rule's keeper" or "any copy under keep". I chose keeper semantics (`design.md`, Open design notes); the scenarios do not tell them apart, so a refinement question at the design gate is cheaper than a test that pins the wrong one.

- **test-author, AC-7 contradicts the core** (test phase): the scenario links a file in B and quarantines A, but `PreviewDeletionPlanService` quarantines a copy only when all its links are under `quarantineIn`, so the scenario yields no operation. The test links both files in A instead; the ticket scenario should be corrected.
- **test-author, TestServer surfaces stubs per call** (test phase): `TestServer.surfaced` takes the recorded exception on any request; in a concurrent test a request on another thread can consume it and show a plain 500. AC-13 therefore makes one sequential read on the test thread first (also red against stubs).

- **verifier, a refinement contradiction found in the test phase reaches the done gate unresolved** (verify phase): the AC-7 contradiction with the core's all-links-under rule was spotted by the test-author, but nothing in the pipeline stops for it, so the AC text and its done-item ("every scenario is an automated test") stay inconsistent until the product-owner review. Suggest the test-author be able to raise a "ticket text contradicts the core" flag that pauses at the next gate, or that refinement for tickets over core semantics check each scenario against the core's rule.
- **verifier, design defers a by-hand check to verify** (verify phase): endpoint checklist item 11 says the dev-proxy POST is "checked once by hand in the verify phase", but `verifier.md` does not list it, and it needs `npm_run_start` plus a fixed-port server. I did not run it. Either add it to the ticket's Definition of done when the design commits to it, or drop the "by hand in verify" wording from the archetype checklist.
- **verifier, Windows curl paths** (verify phase): JSON bodies with backslash paths from Git Bash are easy to break (my first scan POST was malformed and left a `WARN` in the server log). Forward-slash absolute paths (`C:/...`) work and avoid escaping.
